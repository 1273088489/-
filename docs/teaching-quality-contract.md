## 1. 目标与边界

本轮增强现有 MVP 的教学质量，使学习者在每一阶段都能明确学什么、为什么学、按什么流程做、交付什么、如何验证、常见错误是什么，以及怎样复盘并迁移到新问题。

验收证据是：所有用户要求均映射到教学对象和后续任务；课时、练习和阶段项目有统一契约；现有 4 个课时、9 道练习、4 个阶段项目的缺口均已登记；Markdown 与结构化字段的边界已经锁定。

非目标（Phase 1 范围；Phase 2 已扩展部分见下）：隐藏测试、知识图谱、自动补课、复杂个性化推荐、新 AI 基础设施、框架或数据库更换。

> Phase 2 扩展（P2-02/P2-03/P2-04/P2-05/P2-06 已完成）：真实 Git 仓库接入、**受限沙箱内**的用户代码执行、**公开+隐藏测试**与**证据化 AI 评分**已纳入范围——仓库提交在 Docker 容器（无网络、限额资源）中执行 install/build/test 并运行公开/隐藏测试，结果以 `sandbox_run`/`test_case`/`test_run` 证据入库；P2-05 再综合 RepoSnapshot、公开+隐藏测试结果、沙箱运行与仓库文件内容输出结构化评分（score/rubricResults/acceptanceResults/evidenceFacts/capabilityNote），证据持久化到 `evidence_fact`；隐藏测试仅服务端使用，绝不进入公开 API/UI/课程数据。P2-06 个性化补课路径：仓库评审得分未达通过线（或存在失败测试/低分维度）时，规则引擎基于 errorHistory + 测试失败分类 + rubric 低分维度生成有序补课路径（目标 lesson/exercise/project、完成判定），AI 仅增强解释；完成全部补课项后更新项目 mastery/status。隐藏测试只参与服务端分类，其名称与明细绝不进入补课原因文本。文本/代码提交仍不执行。

安全约束：形成性评审不得把未执行的动作报告为已验证——文本提交不得声称运行过代码；仓库提交只有在受限沙箱实际执行过（引用 `sandbox_run` 的 stdout/stderr/exitCode）才能声称“已在沙箱中执行”；未访问的部署地址、未验证的测试结果只能标记为“有证据支持”“无证据支持”或“当前无法验证”。P2-05 证据化评分只引用已采集证据（git_diff/test_output/file_content/runtime），AI 不得臆造测试结果或执行范围，`capabilityNote` 必须如实声明；隐藏测试的名称与明细绝不进入任何面向学习者的反馈文本。

## 3. 内容组织决策

### 3.1 课程阶段

课程保持 4 个学习阶段和 4 个阶段项目，不为了新增课时虚增项目：

1. 工程起点：开发环境、终端、Git，结束于项目 1。
2. 浏览器应用：原生 JavaScript 看板，结束于项目 2。
3. 前端工程化：React 看板，结束于项目 3。
4. 全栈交付：API 与数据库、认证与授权、测试与 CI、Docker 部署与运维，结束于项目 4。

第四阶段包含 4 个课时，因此新增内容后共有 7 个课时。课时标题应表达“课时”，不能继续让“阶段 4”同时指一个课时和一组课时。

### 3.2 Markdown 与结构化字段

| 教学对象 | Markdown 负责 | 结构化字段负责 |
|---|---|---|
| 课时 | 场景、目标、前置、交付物、步骤、概念取舍、常见错误、检查表、复盘 | 继续使用现有课时元数据；本轮不拆正文列 |
| 练习 | 不新增 Markdown 正文 | 继续使用 `prompt`、`hints`、`solution`、`rubric`、题型和选项 |
| 阶段项目 | 背景、目标、前置、过程指南、原因、常见错误、需求变更说明、模板使用说明 | 保留 `tasks`、`acceptanceCriteria`；新增 `guideMarkdown`、`deliverables`、`rubric`、`reflectionQuestions` |
| 学习模板 | 作为相关项目指南中的可复制代码块，并要求实际交付 | 不为 PRD、ER 图、API 契约或 ADR 分别建表 |

选择该边界的原因：长篇教学内容需要可读、可演进的 Markdown；交付物、验收、评分和复盘需要页面、API、审计和评审稳定消费，因此必须结构化。

### 3.3 演示数据策略

课程 API 已经实现，后续不再维护第二套完整教学内容。TQ-02 到 TQ-05 应逐步删除课时、练习和项目页面的课程 demo fallback，让服务端课程定义成为唯一事实来源；网络或认证失败显示明确错误，不用过期课程内容掩盖失败。

首页或无账号演示若仍需要摘要，只保留不含教学正文的展示数据，并用自动测试核对数量和 slug。任何客户端投影都不得包含练习 `solution`。

## 4. 教学内容契约

### 4.1 课时正文

每个 `LessonDef.contentMarkdown` 必须按以下二级标题组织：

1. `阶段位置与真实场景`
2. `学习目标`
3. `前置条件`
4. `本阶段交付物`
5. `实施步骤`
6. `核心概念与取舍`
7. `常见错误与诊断`
8. `完成检查`
9. `复盘与迁移`

学习目标使用“能够 + 动作 + 对象 + 可观察条件”的形式。每个目标至少映射到一道练习或一个项目证据。

“实施步骤”的每一步都必须同时给出：

- 动作：学习者具体做什么。
- 原因：为什么现在做，以及避免什么风险。
- 产出：会创建或改变什么。
- 验证：用什么命令、页面行为或产物检查结果。

“常见错误与诊断”中的每项都必须包含症状、原因、定位方法和修复方向。“复盘与迁移”至少包含一个设计取舍问题和一个新情境迁移问题，不得要求复述正文。

### 4.2 练习

每道练习必须满足：

- `prompt` 指明与学习目标一致的动作、提交内容和作答边界。
- `hints` 至少两级，按“定位问题 -> 指出概念或工具 -> 接近实现路径”递进，不直接泄露完整答案。
- `rubric` 在提交前可见；每项以可观察证据表述，例如“提交中包含 `git status` 的用途及一次预期输出”，不能只写“理解 Git”。
- `solution` 只在允许的反馈流程中使用，不进入公开 API 或客户端 fallback。
- 提交反馈逐项指出已有证据、缺失证据和下一步动作；不能只返回“正确”或“继续打磨”。
- 页面明确说明文本和代码题使用形成性启发式，系统没有运行代码或隐藏测试（仓库提交除外：其在受限沙箱中运行公开与隐藏测试，并基于证据输出评分；隐藏测试内容与明细不对外展示，评分证据展示在项目页）。评审未通过时，项目页与仪表盘展示个性化补课路径（规则引擎映射 + AI 增强解释），完成补课后更新掌握度与状态。

本轮复用现有练习字段，不增加自动判题引擎，也不新增数据库列。

### 4.3 阶段项目

`StageProjectDef` 的目标契约为：

```ts
interface ProjectRubricCriterion {
  id: string;
  criterion: string;
  weight: number;
  evidence: string[];
  levels: {
    excellent: string;
    competent: string;
    developing: string;
    missing: string;
  };
}

interface StageProjectDef {
  // 现有字段保持不变
  guideMarkdown: string;
  deliverables: string[];
  rubric: ProjectRubricCriterion[];
  reflectionQuestions: string[];
}
```

项目字段约束：

- `guideMarkdown` 必须包含目标、前置条件、项目步骤、每步原因、验证、常见错误，以及适用时的需求变更和模板说明。
- `deliverables` 每项都是可提交证据，例如 PRD、Mermaid ER 图、OpenAPI 风格接口契约、ADR、测试报告或部署记录。
- `acceptanceCriteria` 每项只能二值判断，避免“结构清晰”“组件可复用”等无阈值措辞。
- `rubric` 至少 3 个维度，`id` 在项目内唯一，正整数权重总和为 100，每个维度至少一条证据，四个等级描述均非空且可观察。
- `reflectionQuestions` 至少 2 个问题，其中一个必须要求解释设计决策及被放弃方案，另一个必须要求迁移或复盘失败。

评分等级固定为：

| 等级 | 比例 | 含义 |
|---|---:|---|
| excellent | 1.0 | 证据完整、一致，并覆盖边界或权衡 |
| competent | 0.8 | 核心证据完整，可满足预期行为 |
| developing | 0.5 | 有有效尝试，但关键证据或行为不完整 |
| missing | 0.0 | 没有相关证据，或证据与要求冲突 |

总分为各维度 `weight * 等级比例` 之和并四舍五入。验收标准不折算进 rubric 分数；二者分别报告。形成性评审可以判断提交文本是否支持某项验收，但不能把未执行的测试、未访问的 URL 或未读取的 Git 历史报告为已验证。
